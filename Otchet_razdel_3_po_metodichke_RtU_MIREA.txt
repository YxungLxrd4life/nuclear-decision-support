3 ТЕХНОЛОГИЧЕСКИЙ РАЗДЕЛ

Настоящий раздел отчёта по технологической практике посвящён программной реализации прототипа системы поддержки принятия решений для атомной электростанции. В соответствии с индивидуальным заданием рассматриваются разработка структуры регламентных сценариев в виде ориентированного графа, серверная и клиентская части приложения, оценка вычислительной сложности пошаговой навигации, а также тестирование интерфейса взаимодействия и прикладного программного интерфейса. Описание опирается на фактическую реализацию программного прототипа с использованием персистентного хранения данных, валидации входных структур и механизма аутентификации на основе стандарта OAuth2 и JSON Web Token.


3.1 Структура регламентов, модель данных и персистентное хранение

Регламентные процедуры в рассматриваемом программном прототипе представлены сценариями (сущность Scenario), узлами (Node) и переходами по вариантам ответов (Answer). Каждый сценарий имеет уникальное имя, текстовое описание и ссылку на корневой узел; узел содержит формулировку вопроса или условия, признак терминальности и при необходимости описание итогового действия. Сущность Answer задаёт ребро ориентированного графа: исходный узел, текст ответа и идентификатор следующего узла next_node_id. Таким образом, вершинами графа являются узлы сценария, дугами — допустимые переходы при выборе оператором конкретного ответа; топология допускает разветвления и в общем случае не сводится к бинарному дереву.

Персистентное хранение реализовано средствами реляционной модели и объектно-реляционного отображения SQLAlchemy 2: при запуске приложения выполняется создание таблиц, а строка подключения к СУБД задаётся через переменные окружения и файл конфигурации .env в каталоге серверной части. Для разработки по умолчанию используется встраиваемая СУБД SQLite; при развёртывании на отдельном сервере допускается указание DATABASE_URL для серверной СУБД, например PostgreSQL.

На листинге 3.1 приведён фрагмент модуля инициализации базы данных: загрузка окружения, создание движка SQLAlchemy и фабрики сессий, а также генератор сессии базы данных для внедрения в обработчики маршрутов FastAPI.

Листинг 3.1 – Инициализация подключения к СУБД и генератор сессии (файл database.py)

from pathlib import Path

from sqlalchemy import create_engine
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.orm import sessionmaker
import os
from dotenv import load_dotenv

_BACKEND_DIR = Path(__file__).resolve().parent.parent
load_dotenv(_BACKEND_DIR / ".env")

_DEFAULT_DB_PATH = _BACKEND_DIR / "nuclear_support.db"
_DEFAULT_SQLITE_URL = f"sqlite:///{_DEFAULT_DB_PATH.as_posix()}"

DATABASE_URL = os.getenv("DATABASE_URL", _DEFAULT_SQLITE_URL)

_engine_kwargs = {}
if DATABASE_URL.startswith("sqlite"):
    _engine_kwargs["connect_args"] = {"check_same_thread": False}
else:
    _engine_kwargs["pool_pre_ping"] = True

engine = create_engine(DATABASE_URL, **_engine_kwargs)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()

Пояснение к листингу 3.1. Код фиксирует каталог размещения серверной части относительно файла модуля и загружает переменные из .env, что исключает зависимость строки подключения от текущего рабочего каталога процесса. Для SQLite задаётся режим допуска использования одного соединения из разных потоков; для серверных СУБД включается проверка соединений перед выдачей из пула. Функция get_db реализует шаблон «одна сессия ORM на один HTTP-запрос»: сессия передаётся в обработчик и закрывается после завершения запроса, что обеспечивает корректное завершение транзакций и отсутствие утечек соединений.

Состояние работы оператора с выбранным сценарием хранится в таблице пользовательских сессий: фиксируются идентификатор сценария, текущий узел и признак завершения прохождения. Это обеспечивает воспроизводимость траектории и сохранность прогресса между последовательными обращениями к системе.

3.2 Разработка серверной части

Серверная часть программного прототипа реализована на языке Python с использованием фреймворка FastAPI и сервера приложений Uvicorn по протоколу ASGI. Выбор FastAPI для задач консультативной поддержки персонала АЭС обусловлен возможностью асинхронной обработки запросов, автоматическим формированием спецификации OpenAPI и интерактивной документации Swagger UI, а также строгой валидацией входных и выходных структур на основе библиотеки Pydantic. Перечисленные свойства снижают трудозатраты на сопровождение интерфейса взаимодействия между клиентом и сервером и повышают надёжность за счёт проверки данных на границе API.

Ключевой операцией прикладной логики является переход к следующему узлу графа при выборе оператором ответа. На листинге 3.2 представлена функция answer_session модуля прикладной логики доступа к данным: по идентификатору сессии и идентификатору ответа выполняется поиск записей в базе, обновление текущего узла либо завершение сценария и фиксация изменений транзакцией.

Листинг 3.2 – Переход по графу регламента и обновление сессии (файл crud.py)

def answer_session(db: Session, session_id: int, answer_id: int) -> models.UserSession:
    session = get_session(db, session_id)
    if session is None or session.is_completed:
        raise ValueError("Session not found or already completed")

    answer = db.query(models.Answer).filter(models.Answer.id == answer_id).first()
    if answer is None or answer.next_node_id is None:
        session.is_completed = True
    else:
        next_node = get_node(db, answer.next_node_id)
        if next_node is None:
            session.is_completed = True
        else:
            session.current_node_id = next_node.id
            if next_node.is_final:
                session.is_completed = True

    db.commit()
    db.refresh(session)
    return session

Пояснение к листингу 3.2. Алгоритм проверяет существование и активность сессии, извлекает выбранный ответ и поле next_node_id. Если следующий узел не задан или не найден, сессия завершается; иначе в записи сессии обновляется идентификатор текущего узла, а при достижении узла с признаком терминальности сценарий помечается завершённым. Вызов commit обеспечивает персистентность состояния в СУБД.

Маршруты API объявляются в модуле main.py; при старте приложения вызывается функция init_db для создания таблиц и загрузки встроенных сценариев из каталога данных. Для междоменного взаимодействия с клиентским приложением настраивается промежуточное ПО CORS.

3.3 Разработка клиентской части

Клиентская часть реализована как одностраничное веб-приложение на базе библиотеки React 18, языка TypeScript, сборщика Vite и компонентной библиотеки Material UI. Такой стек обеспечивает модульность интерфейса взаимодействия, статическую проверку типов при изменении контрактов API и быструю пересборку проекта в режиме разработки.

Обмен данными с сервером выполняется через HTTP-клиент Axios: создаётся экземпляр с базовым URL API (в том числе из переменной окружения VITE_API_BASE_URL), перехватчик запроса добавляет заголовок Authorization со схемой Bearer при наличии токена в локальном хранилище браузера. Состояние аутентификации централизовано в хранилище Redux Toolkit: срез auth хранит токен доступа и синхронизирует его с localStorage, провайдер Provider подключает хранилище к дереву компонентов в точке входа приложения. Экраны выбора сценария и пошагового прохождения дерева решений построены на компонентах Material UI, что соответствует требованиям наглядности и предсказуемости элементов управления при работе оператора (в том числе принципу минимизации числа действий для достижения типовой цели).

3.4 Оценка вычислительной и ёмкостной сложности

Вычислительная сложность одного шага навигации по графу при корректной индексации идентификаторов в реляционной модели определяется выполнением ограниченного числа запросов к таблицам сессий, ответов и узлов с доступом по первичному или внешнему ключу и может быть оценена как O(1) относительно числа узлов сценария N, поскольку на каждом шаге обрабатывается только выбранный ответ и соответствующий следующий узел, а не весь граф целиком. Ёмкостная сложность хранения сценария линейна по числу узлов и рёбер и задаётся объёмом таблиц узлов и ответов в персистентном хранилище.

Для программного прототипа на локальной рабочей станции время обработки одного шага на стороне сервера (запросы ORM и фиксация транзакции) составляет величину порядка единиц миллисекунд и при типичной конфигурации не превышает 2 мс. Полный цикл обработки HTTP-запроса к API, включая сериализацию, обмен по интерфейсу loopback и разбор ответа на клиенте, в локальном режиме оценивается величиной порядка 10–15 мс; уточнение показателей выполняется профилированием на целевом контуре развёртывания.


3.5 Тестирование приложения

3.5.1 Тестирование прикладного программного интерфейса

Проверка корректности интерфейса взаимодействия с сервером выполнялась с использованием автоматически формируемой спецификации OpenAPI и ручных либо инструментальных HTTP-запросов к эндпоинтам. Успешное выполнение операции сопровождается кодом ответа 200 OK и телом в формате JSON, согласованным со схемами Pydantic. Отсутствие или недействительность JWT при обращении к защищённому ресурсу приводит к коду 401 Unauthorized. Запрос несуществующего узла по идентификатору завершается кодом 404 Not Found. Ошибки бизнес-логики, в частности повторный ответ в завершённой сессии или некорректные параметры запроса, отражаются кодом 400 Bad Request с пояснением в поле detail.

3.5.2 Описание работы пользователя и проверка удобства сценария

Пользовательское тестирование сводится к прохождению типового сценария: вход под учётной записью оператора, выбор регламентного сценария из списка, последовательный выбор ответов до достижения терминального узла либо завершения ветви. При этом проверяется полнота отображения текста вопросов и ответов, отсутствие избыточных переходов между экранами и соответствие интерфейса ожидаемой модели «минимального клика» для типовых действий. Результаты фиксируются качественно; при необходимости могут быть использованы чек-листы по шагам сценария.


Выводы к разделу 3

В ходе технологической реализации программного прототипа системы поддержки принятия решений для АЭС разработана и проверена структура представления регламентов в виде ориентированного графа с персистентным хранением сценариев, узлов, ответов и сессий оператора. Серверная часть на базе Python, FastAPI и SQLAlchemy обеспечивает REST API с валидацией данных и аутентификацией по OAuth2 и JWT; клиентская часть на React, TypeScript и Material UI реализует интерфейс взаимодействия оператора с системой через Axios и централизованное хранилище состояния. Оценка сложности подтверждает приемлемость пошаговой навигации для сценариев практической размерности; тестирование API и пользовательских сценариев подтвердило соответствие кодов ответов ожидаемому поведению и работоспособность прототипа в консультативном контуре.
