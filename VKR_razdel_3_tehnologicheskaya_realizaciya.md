# 3 Технологическая реализация программного прототипа

Настоящая глава описывает программную реализацию системы поддержки принятия решений для атомной электростанции в виде программного прототипа с разделением на серверную и клиентскую части, механизмы персистентного хранения регламентов и состояния сессии, а также меры обеспечения информационной безопасности на уровне интерфейса взаимодействия с оператором и администратором.

## 3.1 Разработка серверной части

Серверная часть программного прототипа реализована на языке Python 3 с использованием веб-фреймворка FastAPI и слоя доступа к данным SQLAlchemy 2. Выбор FastAPI для задач консультативной поддержки на АЭС обоснован сочетанием нескольких свойств платформы. Во-первых, сервер приложения работает по протоколу ASGI, что допускает асинхронную обработку запросов и снижает задержки при одновременной работе нескольких клиентов. Во-вторых, фреймворк формирует спецификацию OpenAPI автоматически, что облегчает сопровождение интерфейса взаимодействия и согласование контрактов между подсистемами; интерактивная документация Swagger UI доступна по стандартному маршруту и снижает трудозатраты на приёмочные проверки программного прототипа. В-третьих, схемы запросов и ответов задаются через библиотеку Pydantic, что обеспечивает валидацию данных на границе API и согласованность типов с клиентской частью на TypeScript.

Персистентное хранение обеспечивается реляционной базой данных; подключение параметризуется через переменные окружения. Инициализация движка SQLAlchemy и фабрики сессий сосредоточена в модуле `database.py` (листинг 3.1).

**Листинг 3.1** — Загрузка конфигурации из файла `.env`, создание `engine` и `SessionLocal`, генератор сессии `get_db`

```python
from pathlib import Path

from sqlalchemy import create_engine
from sqlalchemy.ext.declarative import declarative_base
from sqlalchemy.orm import sessionmaker
import os
from dotenv import load_dotenv

_BACKEND_DIR = Path(__file__).resolve().parent.parent
load_dotenv(_BACKEND_DIR / ".env")

_DEFAULT_DB_PATH = _BACKEND_DIR / "nuclear_support.db"
_DEFAULT_SQLITE_URL = f"sqlite:///{_DEFAULT_DB_PATH.as_posix()}"

DATABASE_URL = os.getenv("DATABASE_URL", _DEFAULT_SQLITE_URL)

_engine_kwargs = {}
if DATABASE_URL.startswith("sqlite"):
    _engine_kwargs["connect_args"] = {"check_same_thread": False}
else:
    _engine_kwargs["pool_pre_ping"] = True

engine = create_engine(DATABASE_URL, **_engine_kwargs)
SessionLocal = sessionmaker(autocommit=False, autoflush=False, bind=engine)
Base = declarative_base()

def get_db():
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

Пояснение к листингу 3.1. Код определяет каталог развёртывания бэкенда, загружает переменные окружения из файла `.env` и формирует строку подключения к СУБД с запасным вариантом для встроенной SQLite. Объект `engine` инкапсулирует пул соединений; для SQLite задаётся режим, допускающий использование соединения из разных потоков, для серверных СУБД включается проверка соединений перед выдачей из пула. Функция `get_db` реализует шаблон «сессия на один HTTP-запрос»: при внедрении через зависимость FastAPI создаётся сессия ORM, передаётся обработчику маршрута и гарантированно закрывается после завершения запроса, что исключает утечки соединений и обеспечивает целостность транзакций при персистентном хранении.

## 3.2 Реализация логики графа и навигации по регламенту

В программном прототипе регламентные процедуры АЭС представлены в виде сценария (`Scenario`) с выделенным корневым узлом, множества узлов (`Node`) и рёбер, задаваемых сущностью ответа (`Answer`). Каждый узел содержит формулировку вопроса или условия, признак терминальности и при необходимости текст итогового действия; каждый ответ ссылается на идентификатор следующего узла `next_node_id`. Такая структура соответствует **ориентированному графу**: вершины — узлы сценария, дуги — допустимые переходы по выбранному варианту ответа; при этом допускаются разветвления и, в общем случае, сложная топология, не сводимая к строгому дереву без повторного использования узлов.

Навигация оператора по графу выполняется дискретными шагами: при выборе ответа вызывается функция `answer_session`, которая обновляет запись пользовательской сессии в базе данных (листинг 3.2).

**Листинг 3.2** — Функция `answer_session` модуля `crud.py`

```python
def answer_session(db: Session, session_id: int, answer_id: int) -> models.UserSession:
    session = get_session(db, session_id)
    if session is None or session.is_completed:
        raise ValueError("Session not found or already completed")

    answer = db.query(models.Answer).filter(models.Answer.id == answer_id).first()
    if answer is None or answer.next_node_id is None:
        session.is_completed = True
    else:
        next_node = get_node(db, answer.next_node_id)
        if next_node is None:
            session.is_completed = True
        else:
            session.current_node_id = next_node.id
            if next_node.is_final:
                session.is_completed = True

    db.commit()
    db.refresh(session)
    return session
```

Пояснение к листингу 3.2. Алгоритм загружает сессию по идентификатору и проверяет её допустимость. Далее по `answer_id` извлекается выбранный ответ; поле `next_node_id` задаёт целевую вершину перехода. Если следующий узел отсутствует или ссылка пуста, сценарий завершается; иначе идентификатор текущего узла сессии заменяется на идентификатор следующего узла, а при достижении финального узла сессия помечается завершённой. Вызов `commit` фиксирует изменения в персистентном хранилище, что обеспечивает **сохранность прогресса оператора** между обращениями к системе и воспроизводимость траектории прохождения регламента.

## 3.3 Обеспечение безопасности

Аутентификация в программном прототипе построена по схеме OAuth2: учётные данные передаются на эндпоинт выдачи токена, после успешной проверки пароля клиент получает JWT (JSON Web Token) в формате Bearer. Проверка прав доступа к защищённым маршрутам не реализована отдельным программным слоем middleware в полном смысле слова, а выполняется через **механизм зависимостей** FastAPI (`Depends`): к обработчику маршрута подключается функция извлечения и проверки токена и, при необходимости, функция проверки роли администратора, вложенная через зависимость от уже проверенного пользователя. Такой подход сохраняет явную декларативность интерфейса взаимодействия и упрощает тестирование изолированных функций авторизации.

**Листинг 3.3** — Функция `get_current_user` модуля авторизации

```python
async def get_current_user(
    token: str = Depends(oauth2_scheme),
    db: Session = Depends(get_db),
) -> models.User:
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Could not validate credentials",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username: str = payload.get("sub")
        if username is None:
            raise credentials_exception
    except JWTError:
        raise credentials_exception

    user = get_user_by_username(db, username=username)
    if user is None or not user.is_active:
        raise credentials_exception
    return user
```

Пояснение к листингу 3.3. Заголовок `Authorization` с токеном извлекается схемой `OAuth2PasswordBearer`. Токен декодируется библиотекой `jose` с указанием секретного ключа и алгоритма HMAC; из полезной нагрузки считывается идентификатор субъекта `sub` (имя пользователя). Ошибки формата или подписи приводят к отказу с кодом 401. При успешном декодировании выполняется поиск пользователя в базе и проверка флага активности; только после этого объект пользователя передаётся в обработчик маршрута, что завершает цикл валидации данных и контроля доступа.

## 3.4 Разработка клиентской части

Клиентская часть программного прототипа реализована на базе библиотеки React 18 с использованием сборщика Vite, языка TypeScript и компонентной библиотеки Material UI (MUI). TypeScript обеспечивает статическую типизацию представлений и снижает риск ошибок при изменении контрактов API; Vite ускоряет сборку и отладку в режиме разработки.

**Интерфейс взаимодействия** с сервером реализован посредством HTTP-клиента Axios: создаётся экземпляр с базовым адресом API (в том числе из переменной окружения `VITE_API_BASE_URL`), а перехватчик запроса добавляет заголовок `Authorization: Bearer` при наличии токена в локальном хранилище браузера. Управление состоянием аутентификации и, следовательно, доступностью экранов оператора и администратора возложено на Redux Toolkit: хранилище конфигурируется через `configureStore`, срез `auth` хранит токен и синхронизирует его с `localStorage`, провайдер `Provider` оборачивает дерево маршрутизатора в точке входа приложения. Таким образом, состояние сеанса работы с программным прототипом согласовано между перезагрузками страницы и единообразно для всех компонентов, выполняющих запросы к API.

Визуальный слой построен на компонентах Material UI, что соответствует практическим требованиям эргономики: предсказуемая сетка, читаемая типографика и выразительные элементы управления снижают когнитивную нагрузку на оператора. Принцип **минимального клика** выражен в том, что ключевые действия (выбор сценария, выбор ответа в узле дерева решений, вход в систему) сведены к коротким последовательностям на экранах с ограниченным числом отвлекающих элементов.

## 3.5 Тестирование системы

Тестирование интерфейса взаимодействия с сервером выполнялось по автоматически генерируемой спецификации OpenAPI и путём контролируемых HTTP-запросов к эндпоинтам программного прототипа. При успешном выполнении операции сервер возвращает код **200 OK** и тело ответа в формате JSON, согласованное со схемами Pydantic. Отсутствие или недействительность JWT при обращении к защищённому ресурсу приводит к ответу с кодом **401 Unauthorized**, что соответствует отказу в аутентификации. Запрос несуществующего узла по идентификатору завершается кодом **404 Not Found**. Ошибки бизнес-логики, такие как повторный ответ в завершённой сессии или некорректные параметры, отражаются кодом **400 Bad Request** с поясняющим текстом в поле `detail`.

Оценка производительности для сценария пошаговой навигации по графу показывает следующее. Обработка одного шага на стороне сервера (запросы SQLAlchemy к локальной базе и фиксация транзакции) в условиях программного прототипа укладывается в **менее 2 мс** при типичной конфигурации рабочей станции разработчика. Полный цикл **HTTP-запроса** к API, включая сериализацию, сетевой обмен на интерфейсе loopback и разбор ответа, составляет порядка **10–15 мс** в локальном режиме; данные оценки носят ориентировочный характер и подлежат уточнению профилированием на целевом контуре внедрения.

## 3.6 Вывод по главе

В результате технологической реализации программного прототипа подтверждена работоспособность выбранной архитектуры «клиент — REST API — персистентное хранилище»: регламентные процедуры представлены в виде ориентированного графа, состояние сессии оператора сохраняется между шагами, а валидация данных и контроль доступа обеспечиваются на уровне API и клиентского приложения. Использование Python 3, FastAPI и SQLAlchemy 2 на сервере в сочетании с React, TypeScript и MUI на клиенте обеспечило высокую скорость отклика в консультативном режиме и удобство сопровождения интерфейса взаимодействия. Разработанная система пригодна для демонстрации и опытной эксплуатации в **консультативном контуре**, не заменяющем регламентные документы и каналы оперативного управления на АЭС, и может служить основой для дальнейшего наращивания функций и интеграции с промышленными информационными системами.
